# Math Games — Pedagogy Redesign: Step 0 Seam Audit

> Generated by the `pedagogy-phase1-seam-audit` Claude Workflow (8 parallel seam readers + 1 synthesis agent). Sizes the LevelManifest blast radius and confirms current state vs the assumptions in `pedagogy-redesign-plan.md`. Companion to that plan; read alongside `AGENTS.md`.

## Executive summary

Today the six-game math-games app threads each game through ONE generic contract — GameModule<TConfig extends {id:string; difficulty:string}> in packages/core/src/game-module.ts — wired into a single registry (apps/web/src/games/registry.ts) and a single generic record-progress pipeline (apps/web/src/games/server-handlers.ts createRecordProgressPipeline). There is NO shared "level/item" type: each of the six games declares its own TConfig (PuzzleConfig, GameConfig, LevelConfig, EquationConfig, FractionConfig, PatternConfig), so "threading a LevelManifest through the level/item contract" means editing the core TConfig bound PLUS six per-game level types PLUS their producers (5 of 6 have seeded generators; pattern-detective is a hand-authored catalog with no generator). None of the proposed manifest fields (skillTags, misconceptionTags, difficultyFeatures, solutionTrace, hintPath, generatorVersion) exist anywhere. GradeBand and a per-attempt table are NOT greenfield: GradeBand already exists as a player-profile literal in packages/core/src/profile.schema.ts (Schema.Literals(['elementary','middle','high'])) and as players.grade_band; a game_attempts event table already exists, is written live on every submission via GameAttemptsService.record, and already has an unused completion_json TEXT slot — so attempt logging is EXTEND/populate, not create. Two cross-cutting hazards recur across seams: (1) the GameModule contract is DUPLICATED — the authoritative copy in packages/core and a stale, drifting mirror at apps/web/src/games/game-module.ts (missing `published`/unlockWhen, no factory) that achievements.logic.ts, server-handlers.ts and routes/achievements.tsx import from — so a manifest added only to core silently won't reach those consumers; (2) solutionTrace/hintPath on level configs would be serialized to the browser via the KV-cached catalog handler unless stripped server-side, leaking solutions. The redesign's downstream goals each have a confirmed but non-trivial anchor: mastery achievements require new fields on AchievementContext + AchievementUnlockCondition (neither carries any skill signal) and reconciling imperative vs declarative achievement evaluation; skill-aware daily requires rewriting the deterministic date-seeded picker and the getDailyPick(hash:number) hook signature (it reads no player data today); misconception feedback requires first converting four LOGIC sites that hardcode English in GameFeedback {kind:'generic';message:string} into a keyed/structured channel, since those strings are currently dead (never rendered) and there are zero feedback.\* i18n keys. The "Cloudflare Workflow item pipeline" is real but narrow: LevelForgeWorkflow (infra/level-forge.worker.ts) is an Alchemy-DSL Workflow that only forges shape-architect SOLUTIONS into KV — it does not generate levels and is unused by the other five games; level generation is lazy seeded pure functions. Levels are never persisted (regenerated deterministically from levelId/seed); only the daily pick metadata (DailyChallengeConfig in dailyChallenges.configJson) and shape-architect solutions (KV) are stored.

## Single-source recommendation

Define LevelManifest, SolutionStep, and HintStep ONCE in packages/core — either inside packages/core/src/game-module.ts (next to the contract) or a sibling packages/core/src/level-manifest.ts — and re-export all three from packages/core/src/index.ts so all six game packages and apps/web import one definition instead of redeclaring level shape. REUSE the existing core GradeBand from packages/core/src/profile.schema.ts for LevelManifest.gradeBand (do NOT introduce a new GradeBand). Attach the manifest by narrowing GameModule's TConfig bound from `{ id: string; difficulty: string }` to `{ id: string; difficulty: string } & LevelManifest` (or add a `manifest: LevelManifest` field), so all six per-game level types (PuzzleConfig/GameConfig/LevelConfig/EquationConfig/FractionConfig/PatternConfig) inherit it via their TConfig rather than each game redeclaring fields. Make the new manifest fields OPTIONAL initially so curated catalog literals and existing test fixtures don't all break, then backfill. CRITICAL PRECONDITION: the stale type-only mirror at apps/web/src/games/game-module.ts (and the duplicated DailyChallengePick/GameProgressRequest) must be deleted or repointed to @math-games/core before/at the same time — otherwise the manifest reaches the core-typed game modules but NOT the central achievement evaluator and server-handlers that import from the duplicate. Reconcile the redesign's generic SolutionStep with the pre-existing shape-architect-internal SolutionStep (packages/game-shape-architect/src/logic/solver.ts) by renaming the internal one or having solutionTrace derive from the existing LevelSolution.steps. pattern-detective's existing per-level `hint?: string` should be reconciled with hintPath/HintStep. For persistence, prefer the already-present game_attempts.completion_json (or a manifest_json TEXT column following the completion_json/config_json precedent) over scattering discrete columns, since D1/SQLite has no native array/json type.

## Stale assumptions — plan claim vs reality

### GradeBand is a new type this redesign introduces.

- **Reality:** REFUTED across 6 of 8 seams. GradeBand already exists as Schema.Literals(['elementary','middle','high']) in packages/core/src/profile.schema.ts, is exported from packages/core/src/index.ts, has matching grade.\* i18n keys (en+vi) in core.ts, and is a live players.grade_band D1 column — but it is bound to the PLAYER, never to a level. (Also duplicated at apps/web/src/player/profile.schema.ts.)
- **Impact on Phase 1:** Phase 1 must REUSE the existing core GradeBand for LevelManifest.gradeBand, not declare a new one. Defining a second GradeBand would create a name collision and split the union. Net new work for gradeBand is only attaching it to the level contract, not type creation; i18n labels for it already exist.

### SolutionStep and HintStep are new types this redesign introduces.

- **Reality:** PARTLY. HintStep is genuinely absent everywhere. But SolutionStep ALREADY EXISTS as a shape-architect-internal solver type (packages/game-shape-architect/src/logic/solver.ts: {pieceId, position, rotation}) and shape-architect's solution.ts packages an ordered path into LevelSolution.steps.
- **Impact on Phase 1:** A new SHARED core SolutionStep will collide by name inside game-shape-architect and must be reconciled (rename the internal type, or have the manifest's solutionTrace reference/derive from the existing LevelSolution.steps). HintStep can be created clean.

### The 'level pipeline' is a Cloudflare Workflow item pipeline (durable WorkflowEntrypoint / step.do generating levels).

- **Reality:** PARTLY. A REAL Cloudflare Workflow exists — LevelForgeWorkflow in infra/level-forge.worker.ts — but it is authored via Alchemy's Effect DSL (Cloudflare.Workflow/task/sleep), not a hand-written WorkflowEntrypoint; Alchemy's makeWorkflowBridge (alchemy@2.0.0-beta.38) generates the WorkflowEntrypoint class and maps task->step.do, sleep->step.sleep at bundle time. Critically it ONLY forges shape-architect SOLUTIONS into KV (key sa:solution:<id>, TTL 30d); it does NOT generate levels and is unused by the other 5 games. Level GENERATION is seeded pure functions (per-game seededGenerator.ts) run lazily via resolveLevelConfig or by the daily cron — not by the Workflow. pattern-detective has NO generator at all (hand-authored catalog).
- **Impact on Phase 1:** generatorVersion does not gate a single durable pipeline; each game owns its own seeded generator (5 of 6) and pattern-detective is hand-authored. A generatorVersion bump must invalidate the forged shape-architect KV pool (level-forge.worker.ts + the cron) but has no effect on the other games' lazy generation. solutionTrace is 'free' only for shape-architect (LevelSolution.steps ready) and largely magic-graph (solver.solve() returns full solutions, currently discarded after masking); PARTIAL for sequence-race (minimax analyzePosition yields one move per call — a full path must be materialized by looping); and must be AUTHORED FRESH for equation-balance, fraction-builder, pattern-detective (closed-form validate() only, no search solver).

### The scoring trio is named resolveLevelConfig / validateGameState / computeScore and lives on the core contract.

- **Reality:** CONFIRMED exact names. They are declared on GameModule<TConfig> in packages/core/src/game-module.ts. Signatures: resolveLevelConfig(levelId:string)=>TConfig|null; validateGameState(level:TConfig, raw:unknown)=>{completed,moves,feedback?}|null; computeScore(ctx:ScoreContext{completed,moves})=>number. core's createValidateAndComputeScore orchestrates resolveLevelConfig -> decode(completionSchema) -> validateGameState -> computeScore -> progressExtras, returning {completed,moves,score,difficulty,isOptimalSolution?,wasWinner?,feedback?}. IMPLEMENTATIONS live per-game in each packages/game-\*/src/module.ts (magic-graph/sequence-race/shape-architect supply validateGameState directly; equation-balance/fraction-builder/pattern-detective supply a `validate` shorthand that createGameModule wraps; pattern-detective also uses the default catalog.find resolveLevelConfig).
- **Impact on Phase 1:** resolveLevelConfig is the natural producer of a manifest-bearing level (returns TConfig). To carry skill/misconception data downstream to attempt logging and mastery achievements, validateAndComputeScore's return shape must also surface manifest fields. Contract lives in one core place; behavior is per-game, so all six module.ts producers must populate the manifest.

### The GameModule / level contract lives in a single place (single-source).

- **Reality:** REFUTED. The contract is DUPLICATED: authoritative packages/core/src/game-module.ts and a stale type-only mirror at apps/web/src/games/game-module.ts (no createGameModule/GameModuleInput, missing `published`, and its Achievement type lacks unlockWhen). The stale copy is imported by achievements.logic.ts, server-handlers.ts, and routes/achievements.tsx. The daily payload also has its OWN Effect Schema.Class (DailyChallengeConfig) plus a duplicated un-validated parseConfigJson in daily-cron.ts; GameProgressRequest is likewise duplicated in core and apps/web.
- **Impact on Phase 1:** A LevelManifest added only to core will NOT reach the central achievement evaluator or server-handlers — the duplicate must be deleted/repointed to @math-games/core first, or every manifest/skill field must be mirrored. This is the single highest-leverage cleanup before slicing; it appears in 5 of 8 seams.

### Threading the manifest through the level/item contract is a self-contained 'Quick win #1' / single type edit.

- **Reality:** REFUTED / PARTLY. There is no single level type; the manifest forces edits across the core TConfig bound + its stale duplicate, all six per-game level types, all six resolveLevelConfig/generator producers, every hand-authored catalog literal (pattern-detective ~18, equation-balance ~16, plus fraction-builder), the KV catalog serializer, daily serialization, the persistence schema + a Drizzle migration, AttemptInput + record() serialization, i18n, and tests — ~167 touchpoints across 8 seams.
- **Impact on Phase 1:** Phase 1 should make the new manifest fields OPTIONAL initially (so curated catalog literals and test fixtures don't all break at once) and backfill, rather than treating this as one atomic edit. Sequence it as: single-source the contract (delete the stale duplicate) -> add optional manifest to core TConfig + reuse GradeBand -> populate per game -> then opt-in persistence/feedback/daily.

### Per-attempt events are not yet logged / attempt logging is greenfield Phase 1 work.

- **Reality:** REFUTED. A game_attempts event table already exists (packages/db/src/schema.ts, migration huge_skin) and is written live on EVERY submission by GameAttemptsService.record (called from server-handlers.ts createRecordProgressPipeline). It already has score/completed/moves/mode + an UNUSED completion_json TEXT column. game_progress (aggregate) and game_attempts (per-event) are BOTH persisted today, in separate (non-batched) inserts.
- **Impact on Phase 1:** Attempt logging is EXTEND/populate, not create. The natural attach point for solutionTrace/skillTags diagnostics is the already-present completion_json (or new columns) on game_attempts; the one live call-site to thread manifest into is server-handlers.ts -> attemptsService.record (currently passes no completionJson, so it is always NULL). Adding columns is an ALTER TABLE migration (pnpm db:generate), and game_attempts.record is its own insert — it plugs in there, NOT into the progress db.batch, unless the pipeline is refactored. There is currently NO test for game_attempts persistence — a coverage gap to fill.

### Achievements can shift from volume-based to mastery-based by changing achievement definitions, and the Achievement type used has unlockWhen.

- **Reality:** PARTLY/REFUTED. Current signals are exclusively volume/completion/difficulty/streak/rank (completed, difficulty, isOptimalSolution=score>=100 proxy, wasWinner, gamesPlayedByType; streak/currentRank exist on the type but are never populated so global_streak_30/global_grandmaster can't fire). NO skill/misconception field exists on AchievementContext or AchievementUnlockCondition. Definitions live in TWO shapes: imperative evaluateAchievements (magic-graph, sequence-race) AND declarative unlockWhen consumed by core's evaluateAchievementsByCondition (the other 4) — plus 4 hard-coded GLOBAL_ACHIEVEMENTS in achievements.logic.ts. The central evaluator imports the Achievement type from the STALE apps/web/src/games/game-module.ts (which lacks unlockWhen), while the game modules import from core (which has it).
- **Impact on Phase 1:** Mastery achievements require: adding skillTags/misconceptionTags (and difficultyFeatures) to AchievementContext + a skill predicate to AchievementUnlockCondition in core; threading the resolved level's manifest into the AchievementContext built in progress.server.ts (the sole evaluator, currently omits skill data); and migrating BOTH the imperative functions AND the declarative predicate engine. fraction-builder's documented difficulty-as-mode proxy (medium=simplify/hard=compare, pinned by catalog.test.ts) is exactly what skillTags should replace. The stale Achievement duplicate must be reconciled or the new fields won't reach the evaluator.

### The daily item can be made skill-aware (spaced review / frontier / stretch) as an additive change.

- **Reality:** CONFIRMED the picker is purely deterministic seeded-by-date and reads NO player data: hash=SHA-256(dateKey) as uint32, game=dailyGameRotation[hash%len], level=configs[hash%len] via getDailyPick(hash:number)=>{levelId,title,difficulty}. Same global item for every player on a date. The dailyChallenges row is GLOBAL (PK challengeDate, one per day) so it cannot hold per-player skill state; a SEPARATE dailyPlayerResults table (PK playerId+challengeDate, written by DailyStreakService) holds per-player history but stores only levelId, no tags. The cron pre-generates today+tomorrow using the same algorithm (player-independent).
- **Impact on Phase 1:** Skill-aware daily is a SUBSTANTIVE REWRITE, not a manifest field add: planDailyChallenge and the getDailyPick(hash:number) hook signature must change to accept player skill state, and the cron's pre-generation assumption (deterministic, player-independent, one row/day) breaks for any per-player targeting. Per-player skill reads would come from dailyPlayerResults (not mentioned in the original plan's file list) or a new skill model.

### Game logic is string-free, so misconception feedback slots cleanly into an already-localized feedback channel; misconception strings have one natural home.

- **Reality:** REFUTED as a current invariant. Four LOGIC sites HARDCODE English in GameFeedback {kind:'generic';message:string}: game-fraction-builder/src/logic.ts ('Denominator cannot be zero.', interpolated equality/simplify/compare), game-pattern-detective/src/logic.ts ('... is not the missing number.'), game-equation-balance/src/logic.ts ('Substituting ... gives ...'), game-shape-architect/src/module.ts validateGameState ('Not all target cells are covered.'). These are plumbed through server-handlers.ts to the client but NEVER rendered (routes show generic localized chips, no .tsx reads feedback.message). Core has ZERO feedback.\* keys — the GameFeedback union is entirely un-localized. Also: per-game keys are UNTYPED (only core has TranslationKey = keyof coreTranslations['en']) and NO test enforces en/vi key parity, so a key added to en can be silently omitted from vi.
- **Impact on Phase 1:** Before misconception feedback can be localized, GameFeedback must first gain a misconception-tag/key+params variant and the four logic sites must be converted from raw English to structured/keyed payloads; routes must be changed to read and localize that payload. New skill._/misconception._ and per-game feedback.\* keys must be added to BOTH en and vi. The natural moment to add a single Object.keys(en) deep-equals Object.keys(vi) parity test (over the merged real dict, not the fabricated 2-key test dict).

### manifest fields seed and generatorVersion are net-new everywhere.

- **Reality:** PARTLY. generatorVersion exists NOWHERE (genuinely new). But `seed` already exists as a column on dailyChallenges and on DailyChallengeRecord/DailyChallengeConfig — though it is `${dateKey}:${gameId}:${levelId}`, an identity/uniqueness key (with a unique index), NOT a generator seed. Per-game generators also take a transient `seed` argument that is consumed only to build the level id string (e.g. practice*${difficulty}*${seed}, eb-${difficulty}-${seed}); it is never stored on a level config. dailyChallenges.configJson is the closest existing analogue to a persisted manifest blob.
- **Impact on Phase 1:** Don't conflate the existing daily `seed` identity string with the manifest's generator seed; they serve different purposes. A per-level/per-manifest seed and generatorVersion are new fields on the level contract. If the manifest is to be persisted per daily challenge it can ride in the existing configJson (or new columns), but per-attempt persistence belongs on game_attempts.

## Open questions to resolve before slicing

- Is the LevelManifest carried as level/CONFIG data (on TConfig, surfaced via resolveLevelConfig) or as a separate GameModule accessor? This determines whether the manifest threads through the catalog (and thus the browser-facing KV catalog payload) or stays server-only.
- Make manifest fields required or optional in Phase 1? Required forces immediate backfill of every curated literal (pattern-detective ~18, equation-balance ~16, plus fraction-builder) and all test fixtures at once; optional + backfill is incremental but lets some games ship without tags. Which?
- Where do solutionTrace and hintPath get STRIPPED before the catalog response, given createGetCatalogHandler serializes configs to the browser via KV JSON? Confirm they must never reach the client to avoid leaking solutions.
- For solutionTrace, accept asymmetric coverage in Phase 1? It is effectively free for shape-architect (LevelSolution.steps) and magic-graph (solver.solve()), partial for sequence-race (loop minimax to build a path), and must be authored fresh for equation-balance/fraction-builder/pattern-detective (no search solver). Should Phase 1 scope solutionTrace only to the solver-backed games?
- Single-source the GameModule contract NOW (delete apps/web/src/games/game-module.ts, repoint achievements.logic.ts/server-handlers.ts/routes/achievements.tsx to @math-games/core) as a prerequisite slice, or thread fields into both copies? The audit treats deleting the duplicate as the highest-leverage cleanup.
- Should manifest-derived analytics (skillTags/misconceptionTags/solutionTrace) be PERSISTED per attempt? If yes, decide: reuse the existing unused game_attempts.completion_json, add a manifest_json TEXT column, or add discrete JSON-TEXT columns — each implies a Drizzle ALTER migration and threading into AttemptInput + the single server-handlers.ts record() call-site (no game_attempts test exists yet).
- How far does skill-aware daily go in Phase 1? Making it spaced-review/frontier/stretch is a rewrite of planDailyChallenge + the getDailyPick(hash:number) hook signature + the cron's player-independent pre-generation assumption, and needs a per-player skill source (dailyPlayerResults or a new model) — not an additive field. Is that in Phase 1 or deferred?
- Does GradeBand need new VALUES for level granularity? The existing player literal is exactly ['elementary','middle','high']; confirm levels can be tagged with the same three bands or whether finer grade bands are needed (which would change the shared union and its i18n).
- For mastery achievements, replace the imperative evaluateAchievements (magic-graph, sequence-race) AND the declarative unlockWhen engine, or migrate everything to one shape? And confirm AchievementContext + AchievementUnlockCondition (core) should gain skillTags/misconceptionTags/difficultyFeatures, plus whether to fix the never-populated streak/currentRank globals at the same time.
- For misconception feedback, will Phase 1 convert GameFeedback to a keyed/structured channel (and update the four hardcoded-English logic sites + the routes that currently drop feedback.message) and add a en/vi parity test? Localizing misconception strings is blocked until the feedback channel is key-based.

## Per-seam detail

### Game registry & app wiring

_Registers each game's GameModule into a single typed registry and wires those modules into routes, server functions (catalog + record-progress), the homepage/daily dashboards, and daily-challenge planning. The registry is the one place that enumerates games and the only intended home for cross-game branching._

**Current state.** Exactly six GameModules are registered in apps/web/src/games/registry.ts (GAME*MODULES = magic-graph, sequence-race, shape-architect, pattern-detective, fraction-builder, equation-balance). There are six matching packages/game-* dirs and six routes/games/\_.tsx. No Function Forge or Pattern Strategist exists anywhere in src or packages (the only "forge" hit is packages/game-shape-architect/src/solution-forge.ts, a solver — unrelated). The authoritative GameModule contract is packages/core/src/game-module.ts, consumed by each game's module.ts via createGameModule(); apps/web/src/games/game-module.ts is a near-duplicate interface (no createGameModule/GameModuleInput, no `published` field) imported only by server-handlers.ts, achievements.logic.ts, and routes/achievements.tsx for typing. The "level/item contract" is the per-game TConfig (EquationConfig in game-equation-balance/src/catalog.ts, PuzzleConfig in game-magic-graph/src/logic/types.ts, etc.), constrained generically only to `{ id: string; difficulty: string }` and supplied via GameModuleInput.catalog: readonly TConfig[]. There is NO shared LevelManifest type; none of the proposed fields (skillTags, misconceptionTags, difficultyFeatures, solutionTrace, hintPath, gradeBand, generatorVersion) exist on any level config, and the literal `LevelManifest` matches nothing. GradeBand DOES already exist, but bound to the player: packages/core/src/profile.schema.ts exports a GradeBand Literals(["elementary","middle","high"]) and players.gradeBand is a DB column — it is not on the level contract. Persistence already serializes a level pick: dailyChallenges.{seed,configJson} in packages/db/src/schema.ts, produced by DailyChallengeConfig + JSON.stringify in apps/web/src/daily/daily.logic.ts; gameAttempts.completionJson stores the player's completion, not the level. Route meta in routes/games/\*.tsx is purely framework wiring (validateSearch/loader/component/errorComponent/pendingComponent); game title/description/route come from the module; mechanic/glyph/pattern are hardcoded gameId→value maps in packages/ui (mechanic-card.tsx GAME_PATTERN, game-glyph.tsx glyphs) and duplicated as GAME_PATTERN in routes/index.tsx — they are not module fields and not declared in route files.

### GameModule contract (the manifest anchor)

_GameModule<TConfig> is the single per-game contract every game package implements and the web app/registry consumes: it bundles catalog access, daily-pick, scoring, achievements, level resolution, and authoritative validation. A LevelManifest threads through its TConfig (the level/item shape) and the validate→score→record path._

**Current state.** The canonical contract is `GameModule<TConfig extends { id: string; difficulty: string }>` in packages/core/src/game-module.ts, re-exported from packages/core/src/index.ts. Its members: id, route, title, description, published?, difficulties, achievements, levelCount, translations, getCatalog(): GameCatalog<TConfig>, getDailyPick(hash)->DailyChallengePick, computeScore(ScoreContext)->number, evaluateAchievements(ctx,unlocked)->string[], progressExtras?(GameProgressInput)->{isOptimalSolution?,wasWinner?}, resolveLevelConfig(levelId)->TConfig|null, validateGameState(level,raw)->{completed,moves,feedback?}|null, and validateAndComputeScore(levelId,completion)->Effect<{completed,moves,score,difficulty,isOptimalSolution?,wasWinner?,feedback?}>. createGameModule(GameModuleInput) is the factory that fills defaults (getCatalog/resolveLevelConfig/getDailyPick/validateGameState/evaluateAchievements) and wires validateAndComputeScore via createValidateAndComputeScore. CRITICAL: TConfig (the level/item type) is NOT declared in core — it is declared independently per game (PuzzleConfig, GameConfig, LevelConfig in each game's logic/types.ts; EquationConfig, FractionConfig, PatternConfig inline in each catalog.ts). Every one is `{ id; difficulty; ...game-specific }` and NONE carries skillTags, misconceptionTags, difficultyFeatures, solutionTrace, hintPath, gradeBand, generatorVersion, or seed. `seed` exists only as a transient generator argument baked into the level `id` string (e.g. `practice_${difficulty}_${seed}`, `eb-${difficulty}-${seed}`). GradeBand ALREADY EXISTS as Schema.Literals(['elementary','middle','high']) in packages/core/src/profile.schema.ts (exported from core index) but is a PLAYER-PROFILE concept, never attached to a level. There is a second, stale, type-only copy of the contract at apps/web/src/games/game-module.ts (no createGameModule, no GameModuleInput, missing the `published` field) consumed by achievements.logic.ts, server-handlers.ts, and routes/achievements.tsx. Catalog (level configs) is serialized to the client via createGetCatalogHandler (KV-cached, JSON) and never persisted to D1; the gameProgress table stores only levelId as a string.

### Authoritative scoring pipeline (record-progress entrypoint -> resolveLevelConfig -> validateGameState -> computeScore -> persist)

_A route POSTs final game state ({levelId, completion}); the server resolves the level config by id, decodes+validates the submitted completion against that config, computes the score server-side (clients never supply scores), then upserts game_progress, inserts a game_attempts row, evaluates achievements, and updates streak/rank/leaderboards._

**Current state.** Per-game server functions (recordMagicGraphProgress, recordShapeArchitectProgress, recordSequenceRaceProgress, recordPatternDetectiveProgress, recordFractionBuilderProgress, recordEquationBalanceProgress) are THIN wrappers: each is createServerFn({method:'POST'}).inputValidator(Schema.decodeUnknownSync(GameProgressRequest)).handler(({data}) => runServerEffect(createRecordProgressPipeline(module, data))). There is ONE generic pipeline: createRecordProgressPipeline(module, data) in apps/web/src/games/server-handlers.ts. It calls module.validateAndComputeScore(data.levelId, data.completion) -> recordGameProgress({playerId, gameId, levelId, ...result}) -> attemptsService.record(...) -> analytics -> (optional) DailyStreakService -> RankService -> recordLeaderboardEntries.

The scoring trio lives on the PER-GAME module (the GameModule<TConfig> contract in packages/core/src/game-module.ts), NOT as standalone core functions. core's createValidateAndComputeScore is the orchestrator that, given a module's {completionSchema, resolveLevelConfig, validateGameState, computeScore, progressExtras}, runs: resolveLevelConfig(levelId) -> (null => GameProgressValidationError 'Unknown level') -> Schema.decodeUnknownSync(completionSchema)(raw) -> validateGameState(level, parsed) -> (null => 'Invalid game state') -> computeScore({completed, moves}) -> progressExtras(...). It returns {completed, moves, score, difficulty, isOptimalSolution?, wasWinner?, feedback?}. Signatures: resolveLevelConfig:(levelId:string)=>TConfig|null; validateGameState:(level:TConfig, raw:unknown)=>{completed,moves,feedback?}|null; computeScore:(ctx:ScoreContext{completed,moves})=>number.

createGameModule (core) wires defaults: if a module supplies `validate` instead of `validateGameState` (equation-balance, fraction-builder, pattern-detective do this), createGameModule synthesizes validateGameState = decode-then-validate; magic-graph/shape-architect/sequence-race supply validateGameState directly and decode raw inside it. TConfig is the per-game level/item type: PuzzleConfig (magic-graph), LevelConfig (shape-architect), GameConfig (sequence-race), EquationConfig, FractionConfig, PatternConfig. Each only requires {id, difficulty} structurally; none has skill/misconception/grade/seed/trace/hint fields today. The ONLY level metadata that currently flows out of the pipeline is `difficulty` (read off level.difficulty).

Client payload = GameProgressRequest (Schema.Class, duplicated identically in packages/core/src/game-progress.schema.ts and apps/web/src/games/game-progress.schema.ts): {levelId: NonEmptyString, completion: Unknown(non-null), challengeDate?: NonEmptyString, turnstileToken?: String}. No score, no skill data. Server persists to game_progress (PK player+game+level: bestScore=max, attempts+1, completedAt) and game_attempts (score, completed, moves, mode, durationMs?, completionJson?). NOTE: game_attempts.completion_json column and AttemptInput.completionJson exist but the pipeline NEVER passes them (always NULL) — that is the natural attach point for solutionTrace/skillTags diagnostic logging. GradeBand ALREADY EXISTS in core (profile.schema.ts: Schema.Literals(['elementary','middle','high']), exported from @math-games/core) as a player-profile field — the plan's claim that GradeBand is new is only partly true.
