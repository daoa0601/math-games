# Codebase audit — 2026-06-11

Multi-agent audit (41 agents: 6 dimension surveyors + adversarial verification of every medium/high finding against the code on disk). **35 findings confirmed, 0 refuted**, 17 low-severity items unverified. Working tree at time of audit included uncommitted Slice 4 WIP.

Severity = impact if unaddressed. Effort = small (≤1 file / ≤1 hr), medium (one seam, a few files), large.

## Server performance (Workers + D1)

### [HIGH / effort: small] Hourly rate limiter is a no-op: KV cache get() rejects primitive values, so the counter never increments past 1

**File:** `packages/effect-infra/src/kv-cache.ts:29`

**Evidence:** kv-cache.ts get() parses then discards primitives: `const parsed: unknown = JSON.parse(raw); if (parsed === null || typeof parsed !== "object") return null;` (lines 28-30). rate-limit.ts assertHourlyLimit stores a number: `const current = yield* kvCache.get<number>(kvKey); const count = (current ?? 0) + 1; if (count > max) return yield* new RateLimitError({ key }); yield* kvCache.put(kvKey, count, 3600);` (lines 70-75). Since JSON.parse("1") is typeof "number", get() always returns null, count is always 1, and the limit `assertHourlyLimit(`progress:${playerId}`, 200)` invoked on every progress submission (apps/web/src/games/server-handlers.ts:91) can never trigger. Meanwhile every record-progress request still pays one KV read + one KV write (and KV has a 1 write/sec/key limit, silently swallowed by the put's catch). The only test KV layer stubs get() to null (packages/effect-infra/src/**tests**/rate-limit.test.ts:20-24) and assertHourlyLimit has zero test coverage, so this is invisible to CI.

**Recommendation:** Fix KvCacheShape.get to accept primitives (return `parsed as T` after JSON.parse without the typeof-object guard, or add a dedicated getNumber). Then add a test that drives assertHourlyLimit past `max` and asserts RateLimitError. Longer term, a read-modify-write counter in eventually-consistent KV undercounts under concurrency — consider keying per-isolate tolerance or moving the quota to D1/Durable Objects if it must be accurate. This restores the only volume-based abuse guard on the score-recording write path and stops paying 2 KV ops per request for a counter that does nothing.

### [HIGH / effort: medium] Record-progress hot path issues 6-10 sequential D1 round trips per submission; related writes are split across non-atomic statements

**File:** `apps/web/src/games/server-handlers.ts:110`

**Evidence:** createRecordProgressPipeline runs strictly sequentially via Effect.gen: recordGameProgress (1 batched read RT + 1 batched write RT, progress.server.ts:53-167), then attemptsService.record (separate insert RT, game-attempts.ts:82-100), then for daily: streak upsert + 90-row streak read (2 RTs, daily-streak.ts:126-174), then rankService.computeRankDelta (1 batched read RT, rank.ts:30-52), then recordLeaderboardEntries: personal upsert (1 RT) + classroomMembers select (1 RT) + a per-classroom loop `for (const row of classroomRows) { yield* leaderboard.recordEntry({...}) }` (server-handlers.ts:252-254) — one more RT per classroom. A practice submission is ~6+N sequential D1 round trips; daily is ~9+N. CLAUDE.md mandates `db.batch([...])` for atomic multi-statement writes, yet the gameAttempts insert, dailyPlayerResults upsert, and leaderboard upserts each ship as standalone statements — if one fails after recordGameProgress committed, progress/attempts/leaderboard diverge.

**Recommendation:** Consolidate: (1) merge the three read groups (existing achievements + attempts-by-game, rank counts, classroom memberships) into one db.batch read up front; (2) merge all writes — players upsert, gameProgress upsert, achievements insert, gameAttempts insert, dailyPlayerResults upsert, personal + classroom leaderboard upserts — into a single db.batch (D1 batches are atomic), building classroom upserts from the batched membership read. This cuts per-submission latency from ~6-10 D1 RTs to ~2-3 and makes the write set atomic.

### [HIGH / effort: small] game_attempts has no secondary index — every per-player/per-game query is a full scan of the fastest-growing table

**File:** `packages/db/src/schema.ts:90`

**Evidence:** schema.ts defines gameAttempts with only `id: text("id").primaryKey()` (lines 90-106) and the migration (packages/db/drizzle/migrations/20260516024706_huge_skin/migration.sql) confirms no CREATE INDEX on it; the only indexes in any migration are daily_challenges_seed_idx and players_display_name_idx. But the table is queried by player/game everywhere: getPerGameStats `WHERE player_id GROUP BY game_id` (packages/effect-game/src/game-attempts.ts:188-196) runs on every player's first daily-challenge load of the day (apps/web/src/daily/daily.server.ts:62-64); getHistory/getStats filter (playerId, gameId[, levelId]) (game-attempts.ts:117-126, 136-164); classroom getMembers runs a correlated `(select count(*) from game_attempts where player_id = ...)` per member (packages/effect-classroom/src/classroom.ts:235) — O(members x total_attempts); analytics-dashboard.ts filters by created_at range and gameId (lines 67-108, 134-143). One row is appended per game submission, so these scans degrade linearly forever.

**Recommendation:** Add a composite index `ON game_attempts (player_id, game_id, created_at)` (covers getPerGameStats, getStats, getHistory, and the getMembers subquery) and, if the teacher dashboard matters, `ON game_attempts (created_at)` and/or `(game_id, level_id)` for the date-range and level-difficulty reports. Run `pnpm db:generate` for the migration. This turns the hottest read shapes from full scans into index seeks.

### [MEDIUM / effort: small] Classroom leaderboard and classroom_members player lookups cannot use any index (wrong PK column order, no secondary index)

**File:** `packages/db/src/schema.ts:165`

**Evidence:** leaderboardEntries' only index is the PK `(playerId, gameId, levelId, scope)` (schema.ts:180-184), but getClassroomLeaderboard filters `WHERE game_id = ? AND level_id = ? AND scope = ? ### [MEDIUM / effort: small] Daily challenge GET writes to D1 (players upsert) on every request, even when the KV cache hits

**File:** `apps/web/src/daily/daily.server.ts:112`

**Evidence:** loadDailyChallenge unconditionally runs `db.insert(schema.players).values(identity).onConflictDoUpdate(...)` (lines 112-124) BEFORE the cache check `const cached = yield* kvCache.get<DailyChallengeRecord>(cacheKey); if (cached) return cached` (lines 130-131). The comment says the upsert exists only for FK safety of player_daily_selections inserts — but on a cache hit no insert ever happens, so the hot path (every /daily page view, response is also `cache-control: no-store` per daily.functions.ts:12) pays a D1 write + KV read when it needs only the KV read. D1 writes are the scarcest resource here (single-writer, billed per row written).

**Recommendation:** Move the players upsert inside loadDailyChallengeForPlayer, just before the playerDailySelections insert (the only statement needing the FK parent) — or make it the first statement of a db.batch with that insert. Cache-hit requests then become KV-only, removing one D1 write per daily view for every returning player.

### [MEDIUM / effort: small] Catalog handler round-trips to KV on every request to cache data that is already a static in-memory constant

**File:** `apps/web/src/games/server-handlers.ts:45`

**Evidence:** createGetCatalogHandler does `const cached = yield* kvCache.get<Catalog>(`catalog:${module.id}`); if (cached) return cached;` then on miss `toClientCatalog(module.getCatalog())` + `kvCache.put(...)` (lines 58-69). But every game's catalog is computed at module load from bundled data — e.g. magic-graph: `const cachedCatalog = getMagicGraphCatalog();` (packages/game-magic-graph/src/module.ts:37) and the createGameModule default getCatalog just wraps the static array (packages/core/src/game-module.ts:278-284). toClientCatalog is a pure synchronous field-strip. So the KV read (network hop + JSON.parse of the full catalog) is strictly slower than reading isolate memory, and the put adds KV write cost — the cache can never be fresher or cheaper than its source.

**Recommendation:** Replace the KV layer with a module-level memoized constant: compute `toClientCatalog(module.getCatalog())` once per module (e.g. a lazily-initialized Map keyed by module.id in server-handlers.ts) and return it directly, keeping the existing `cache-control: public, max-age=300` header for client/CDN caching. Removes one KV read per catalog request and the KV writes entirely.

## Client performance (bundle + runtime)

### [HIGH / effort: small] three.js (650KB raw / 167KB gz) loads eagerly on every route, including the homepage — the lazy import is fully defeated

**File:** `packages/game-shape-architect/src/index.ts:7`

**Evidence:** The barrel re-exports the three.js renderer: `export * from "./rendering/three-scene"` (index.ts:7), and three-scene.ts statically imports `* as THREE from "three"` + OrbitControls (three-scene.ts:1-2). ShapeArchitect3D.tsx tries to lazy-load it via `import('@math-games/game-shape-architect').then(({ createThreeScene }) => ...)` (ShapeArchitect3D.tsx:92), but the same barrel module is statically imported everywhere: `apps/web/src/games/registry.ts:5` imports `shapeArchitectModule`, and `apps/web/src/routes/-root-components.tsx:7,10` (rendered on every page) imports `translations`/`PUBLISHED_GAME_MODULES`, which pull the barrel through `apps/web/src/i18n-translations.ts:2`. Because the barrel is statically reachable AND its `createThreeScene` export is marked used by the dynamic import, Rollup keeps three.js in the statically-loaded shared chunk. Verified in the production build: `dist/client/assets/src-CIgOdw2a.js` (650,185 B raw, 167,496 B gzip) contains `three.js r184`, `WebGLRenderer`, `OrbitControls`; it is imported with a top-level `from"./src-CIgOdw2a.js"` by the entry chunk `index-DKP2LcdJ.js` (contains hydrateRoot) and by `registry-DHOmHkBn.js`. The 'lazy' `import()` in the shape-architect chunk compiles to `import("./src-CIgOdw2a.js")` — the chunk is already loaded, so the split is a no-op. Net: ~167KB gz of WebGL code is parsed before hydration on the dashboard, profile, daily, and all five non-3D games.

**Recommendation:** Remove `export * from "./rendering/three-scene"` from packages/game-shape-architect/src/index.ts and expose it as a subpath export instead (the package already does this for `./forge` in package.json). In ShapeArchitect3D.tsx, dynamic-import the subpath directly (`import('@math-games/game-shape-architect/three-scene')`) and keep the `ThreeScene` type as an `import type` from that subpath. Rebuild and confirm three.js lands in its own async chunk fetched only when the user toggles the 3D view. This removes ~167KB gz from the critical path of every page — by far the largest single win available.

### [HIGH / effort: small] 3D mode rebuilds the entire three.js scene (dispose + recreate all meshes/materials) every second because gridState gets a new identity on every render

**File:** `apps/web/src/routes/games/-shape-architect-route.tsx:685`

**Evidence:** The route passes `gridState={grid.toNestedArray()}` (line 685) — `toNestedArray()` (packages/game-shape-architect/src/logic/voxel-grid.ts:66) allocates a fresh nested array on every call. ShapeArchitectRoute re-renders at least once per second while playing, because `useGameSession` runs `setInterval(() => setElapsedSeconds(s => s + 1), 1000)` (packages/ui/src/use-game-session.ts:28-31) in the same component. ShapeArchitect3D then re-runs `useEffect(() => { sceneRef.current?.updateGrid(gridState, config, placedPieces) }, [gridState, config, placedPieces, ready])` (ShapeArchitect3D.tsx:127-129) on every tick, and `updateGrid` (packages/game-shape-architect/src/rendering/three-scene.ts:163-235) calls `clearGroup()` twice — disposing every geometry/material — then recreates one `LineSegments` per target voxel and new `MeshStandardMaterial` + `InstancedMesh` per color, re-uploading instance matrices to the GPU. The same new-identity prop also forces `VoxelGrid.fromNestedArray` and the ghost-piece search (`findNearestValidPosition`) to recompute each render (ShapeArchitect3D.tsx:55-84).

**Recommendation:** Memoize the serialization in the route: `const gridState = useMemo(() => grid.toNestedArray(), [grid])` (or pass the `VoxelGrid` instance and convert inside a memo). `grid` already has stable identity (`serverGrid` is memoized on `serverState.grid`, `optimisticGrid` is state), so the effect would then fire only on real grid changes. This eliminates a full scene teardown/rebuild + GPU buffer upload every second (and the resulting GC/frame hitches on the low-end devices kids use) for the cost of one line.

### [MEDIUM / effort: small] three.js scene renders continuously at full FPS with shadow maps and preserveDrawingBuffer even when completely idle

**File:** `packages/game-shape-architect/src/rendering/three-scene.ts:327-331`

**Evidence:** `function animate() { animationId = requestAnimationFrame(animate); controls.update(); renderer.render(scene, camera); }` runs unconditionally from scene creation (line 345) until dispose — re-rendering a static voxel board at device refresh rate (60-120fps) with `renderer.shadowMap.enabled = true` and a 1024x1024 shadow map (lines 80-81, 101) while the student is just thinking. The renderer is also created with `preserveDrawingBuffer: true` (line 77), which disables buffer-swap optimizations and increases memory, and nothing in the codebase reads the canvas back (no toDataURL/screenshot usage).

**Recommendation:** Switch to on-demand rendering: render once after `updateGrid`/`updateGhost`/`fitToGrid`/`resize`, and while OrbitControls damping is active drive frames from the controls' 'change'/interaction events (a small `needsRender` flag loop that idles when nothing changed). Drop `preserveDrawingBuffer: true` unless screenshots are planned. This cuts sustained GPU/CPU/battery drain to near zero during the long idle stretches typical of a puzzle game.
